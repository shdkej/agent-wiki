# 관측 가능한 피드백 시스템

운영 가능한 시스템은 좋은 의도보다 먼저 `지금 무슨 일이 일어나는지`를 볼 수 있어야 한다. 이 합성은 [Monitoring](/docs/mapped/deep-knowledge/monitoring), [Feedback](/docs/mapped/Communication/Feedback), [Life Tracking](/docs/mapped/blog/Life_Tracking), [Journal](/docs/mapped/Idea/Journal), [Note Management](/docs/mapped/blog/Note_Management)에 반복되는 판단을 하나로 묶는다.

## 핵심 판단

관측은 수집량의 문제가 아니라 **다음 행동으로 돌아오는 신호의 수명주기**다. 로그, 메트릭, 알림, 회고, 생활 기록, 노트 링크가 많아도 다음 조정으로 이어지지 않으면 보관만 늘어난다. 반대로 적은 신호라도 정상 상태, 이상 징후, 재진입 위치, 다음 행동이 함께 남으면 운영 판단이 된다.

## 반복 구조

| 단계 | 시스템 운영 | 생활/지식 운영 | 판단 기준 |
| --- | --- | --- | --- |
| 정상 상태 정의 | 로그인, 결제, API latency, 비용, 퍼널 | 수면, 작업, 식사, 이동, 하루 맥락 | 무엇을 지키려는지 먼저 말로 정한다 |
| 신호 수집 | 로그, 메트릭, 트레이스, 사용자 행동 | 캘린더, 사진, 메모, 저널, 리마인더 | 많이 모으기보다 나중에 해석 가능한 단서를 남긴다 |
| 신호 선별 | 깨우는 알림, 대시보드, 진단 로그 | 하루 요약, 주간 회고, 다시 볼 노트 | 모든 신호를 같은 채널과 같은 속도로 보내지 않는다 |
| 재진입 | 장애 원인 조사, 롤백, 개선 실험 | 내일 조정, 발행 후보, 루틴 변경 | 신호가 다음 행동을 부르지 못하면 피드백 루프가 닫히지 않는다 |

## 세 노드가 같은 말을 하는 지점

`Monitoring`은 서버가 살아 있는지만 보지 않고, 사용자가 실제로 가치를 받고 있는지까지 정상 상태에 포함한다. 그래서 시스템 지표와 비즈니스 지표, 꼬리 latency, 비용 스파이크, 알림 피로를 한 운영면에서 읽는다.

`Feedback`은 사람의 코멘트와 소프트웨어 알림을 같은 구조로 본다. 피드백은 평가 문장이 아니라 `수집 / 선별 / 해석 / 재호출`을 지나 다음 시도를 바꾸는 회로다.

`Life Tracking`은 생활 데이터를 많이 쌓는 취미가 아니라 하루를 다시 읽고 내일 한 가지를 조정하는 파이프라인이다. 자동 수집, 반자동 입력, 사람이 남기는 해석을 나누어야 지속된다.

이 셋을 묶으면 공통 결론은 분명하다. 사용자는 관측 도구 자체보다 **관측된 신호가 언제 사람의 주의를 부르고, 언제 조용히 쌓이며, 언제 다음 행동으로 압축되는지**를 더 중요하게 본다.

## 적용 기준

- 새 로그나 지표를 추가하기 전에 `이 신호가 어떤 정상 상태를 증명하는가`를 먼저 묻는다.
- 알림은 지표 초과가 아니라 지금 개입하지 않으면 사용자 가치, 비용, 신뢰가 망가지는 경우에만 강하게 승격한다.
- 회고와 대시보드는 모든 원인을 설명하려 하지 말고 다음 재진입 질문 하나를 남긴다.
- 생활 기록과 시스템 관측 모두 자동 수집층, 확인층, 행동 조정층을 분리한다.
- 발행이나 보고로 넘길 때는 원자료 전체가 아니라 반복 가능한 판단 구조만 추출한다.

## 경계

이 합성은 새 모니터링 도구 목록이나 생산성 앱 추천이 아니다. 도구 선택은 각 mapped 노트의 원문 경계 안에 남긴다. 여기서는 여러 노트가 공유하는 판단, 즉 `볼 수 있어야 고칠 수 있지만, 고치게 만들지 못하는 관측은 운영 자산이 아니다`라는 기준만 보존한다.
