- 상태: 초안 · 완벽한 첫 구조보다 변경 반경, 상태 소유권, 검증 리듬을 먼저 고정하는 판단 모델

## 한 줄 요약

변경 친화적인 구조는 나중에 아무렇게나 바꾸기 쉬운 구조가 아니라, 무엇이 바뀌고 무엇이 남아야 하는지의 경계와 검증 표면을 미리 남겨 두는 운영 방식이다.

## 중심 판단

Architecture, Software, Coding, Deploy ERP 사례는 모두 다른 층위를 말하지만 같은 결론으로 모인다. 좋은 구조는 처음 선택한 패턴 이름보다, 변경이 생겼을 때 어디까지 흔들리고 어디서 멈출지 설명할 수 있는가로 판정된다.

이 판단은 느슨한 결합을 추상 미덕으로 두지 않는다. 결합을 낮춘다는 말은 실제로는 상태 소유자, 실행 계약, 실패 책임, 재검증 방법을 나눠 적는 일이다. 그 네 가지가 없으면 모듈을 나눠도 운영자는 여전히 어디를 고쳐야 하는지 알 수 없다.

## 네 개의 고정점

| 고정점 | 판단 질문 | 깨질 때 보이는 증상 |
| --- | --- | --- |
| 변경 반경 | 이 변경은 어느 모듈, 설정, 문서, 데이터까지 흔드는가? | 작은 수정이 주변 파일과 배포 절차까지 번진다. |
| 상태 소유권 | 이 상태는 코드, 이미지, 볼륨, DB, 사용자 설정 중 어디에 남는가? | 재시작이나 재배포 뒤 방금 고친 내용이 사라지거나, 잃으면 안 되는 데이터가 빌드 산출물처럼 취급된다. |
| 실패 책임 | 실패는 하위 모듈이 복구하는가, 호출자가 선택하는가, 운영자가 멈추는가? | 에러가 숨거나, 반대로 모든 계층이 같은 실패를 중복 처리한다. |
| 검증 리듬 | 바꾼 뒤 무엇을 보면 정상이라고 말할 수 있는가? | 테스트, 화면 확인, 로그, 문서 갱신이 분리되어 변경 완료 기준이 흐려진다. |

## 반복 패턴

### 1. 세부 결정은 늦추되 기준선은 늦추지 않는다

Architecture 노트는 세부사항 결정을 가능한 한 늦추고, 변하는 것과 변하지 않는 것을 나누라고 본다. 여기서 늦춘다는 말은 결정을 회피한다는 뜻이 아니다. 먼저 정책, 기본값, 오버라이드 표면을 정하고 세부 구현은 교체 가능하게 남긴다는 뜻이다.

### 2. 변경 가능성은 상태 생애주기와 붙어 있다

Software 노트는 삭제, 트랜잭션, 캐시, 버저닝, EOL을 상태 변화의 흔적으로 읽는다. 빠르게 바꾸는 능력만으로는 충분하지 않다. 바뀐 뒤에도 왜 바뀌었고, 무엇을 되돌릴 수 있고, 사용자에게 어떤 종료 조건을 알려야 하는지가 남아야 변경 가능성이 운영 자산이 된다.

### 3. 코드는 실패 경로를 드러낼 때 오래 간다

Coding 노트는 SOLID, DI, 테스트, 빠른 리턴, 에러 전파를 모두 변경 반경과 복구 가능성의 언어로 묶는다. 좋은 코드는 해피 패스를 짧게 만드는 코드보다, 실패했을 때 호출자와 운영자가 다음 행동을 고를 수 있게 하는 코드다.

### 4. 실습의 깨짐은 구조 전환 신호다

Deploy ERP 노트에서 컨테이너 안 직접 수정이 `down/up` 뒤 사라진 경험은 단순 실수가 아니다. 런타임 수정, 빌드 정의, addon, 볼륨, DB 데이터를 서로 다른 표면으로 나눠야 한다는 신호다. `docker-compose.yml` 하나로 끝내고 싶은 욕구는 결국 실행 계약, 빌드 계약, 보존 계약을 분리하는 방향으로 성숙한다.

## Knowledge Lab 재사용 기준

- 기술 선택이나 구조 논의를 평가할 때는 먼저 `변경 반경 / 상태 소유권 / 실패 책임 / 검증 리듬` 네 칸으로 나눈다.
- 특정 패턴 이름이 등장해도, 그 패턴이 어떤 결정을 늦추고 어떤 기준선을 고정하는지 설명되지 않으면 synthesis에 승격하지 않는다.
- 실습형 노트의 오타, 거친 명령, 화면 확인은 최신 정답으로 덮지 않고, 어떤 운영 계약이 아직 문서화되지 않았는지 보여 주는 증거로 둔다.
- 향후 DevOps, Infra, Container, Troubleshooting 노트에서 같은 판단이 반복되면 이 페이지는 "구조 이름 비교"가 아니라 "변경 완료 기준"을 묻는 연결면으로 쓴다.
