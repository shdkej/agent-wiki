# 확장 전에 구조를 본다

범위, 수량, 장치, 시스템을 늘리기 전에 먼저 현재 구조의 경계와 병목을 확인한다. 이 개념은 "더 많이 붙이기"보다 읽기/쓰기, 실시간/사전 계산, 핵심/비핵심, 탐지/제어처럼 책임을 나누는 판단을 우선한다.
아이디어가 여러 갈래로 흩어질 때도 먼저 `문제 / 장면 / 루프 / 첫 결과물`로 압축하면, 어떤 트랙에 둘지 빨리 보인다.
생성형 작업에서는 결과를 바로 밀어 넣기보다, 이미지나 장면의 순서 같은 구조를 먼저 고정하는 편이 낫다.

## Why it matters
구조를 먼저 보면 확장은 단순 증설이 아니라 위험을 어디서 흡수할지 정하는 일이 된다. 기존 플랫폼이나 맥락 경계가 이미 문제를 해결하는지 확인하고, 부족할 때만 새 층을 추가한다. 이 판단에는 내용의 양뿐 아니라 **읽히는 순서**도 들어간다. 한 화면에 뭉친 기록은 먼저 제목-섹션-본문 순서로 풀어야 무엇이 먼저 보여야 하는지 드러난다. 그래서 이 개념은 과잉 구축을 줄이는 동시에, 진짜 피크나 장애 상황에서는 어떤 방어선이 먼저 작동해야 하는지도 선명하게 만든다.

## 판단 패턴

- 읽기 폭주는 쓰기 시스템과 분리해 흡수한다.
- 반복 조회와 복잡 계산은 요청 시점보다 사전 계산·캐시 워밍으로 옮긴다.
- 데이터 정합성이 중요한 구간은 빠른 검사, 분산 락, 데이터베이스 최종 방어처럼 층을 나눈다.
- 장애 대응은 알림을 늘리는 것이 아니라 이상 징후 탐지와 즉시 끌 수 있는 제어면을 함께 둔다.
- 한 덩어리로 뭉친 기록은 내용을 더하기 전에 먼저 섹션과 빈 줄로 나눠 읽히는 순서를 만든다.
- 여러 갈래 잡상은 먼저 `문제 / 장면 / 루프 / 첫 결과물` 네 칸으로 압축한 뒤, 책/공간/루프/제출 중 어디에 둘지 정한다.
- 이미지 묶음이나 영상 후보는 생성 전에 순서와 스토리보드를 먼저 정한다.

외부 링크 `source/external-links/ai-agents/2026-05-01-musinsa-techblog-growth-story.md`는 무신사 무진장 이벤트 시스템 사례를 통해 이 패턴을 잘 보여준다. 분당 수백만 조회와 주문 피크를 하나의 성능 문제로 보지 않고, CQRS/Redis로 조회를 격리하고, 쿠폰 계산을 사전 인덱싱으로 옮기고, AIOps와 feature flag를 탐지-제어 쌍으로 묶었다. 여기서 배울 점은 특정 기술명이 아니라, 성장 압력이 커질수록 먼저 책임 경계를 쪼개고 각 경계마다 실패 흡수 방식을 정해야 한다는 점이다.
